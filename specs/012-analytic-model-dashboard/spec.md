# Feature Specification: Analytic Dashboard for Model Outputs

**Feature Branch**: `012-analytic-model-dashboard`

**Created**: 2026-06-01

**Status**: Draft

**Input**: Natural successor to SPEC-011 (honest model bake-off). Expose modeling results from SPEC-011 in a dashboard-grade static analytic report with 11 panels and a TRIPOD-AI model card. The dashboard must read model output files, not retrain models during rendering. Implements P7 (honest evaluation), P8 (clinical fidelity), P9 (synthetic-data transparency), and P10 (equity-centered design). Depends on SPEC-001 schema roles, SPEC-004 visualization foundation, SPEC-007 EDA CLI pattern, and SPEC-011 modeling artifacts.

## Scope

SPEC-012 adds a static analytic reporting layer over the model bake-off. The dashboard reads completed SPEC-011 artifacts from `outputs/modeling/` (or a configured directory), renders 11 panel figures to `outputs/figures/analytic/`, and generates a TRIPOD-AI model card. It does not train or score any model. Every financial assumption required by the alarm-cost panel is read from `config/costs.yaml` — no hardcoded finance values in plotting code.

All outputs MUST be framed as synthetic-data signal characterization when run on bundled synthetic data, and as candidate-model characterization otherwise. No panel may imply validated clinical performance.

## Clarifications

### Session 2026-06-01

- Q: Should SPEC-012 retrain or re-score any model during rendering? → A: No. Every panel reads pre-generated SPEC-011 artifact files. Rendering failure due to a missing optional input renders an explicit unavailable panel, not a silent skip.
- Q: What is the primary metric ordering for the leaderboard? → A: AUPRC is the primary sort key; recall at fixed precision and Brier score are co-headlined; AUROC may appear as a secondary column but must not be visually primary or labeled as primary.
- Q: How should the alarm-cost panel handle sensitivity ranges? → A: Read all sensitivity ranges from `config/costs.yaml`. No fallback hard-coded values are permitted.
- Q: What framing is required on the TRIPOD-AI model card when synthetic data are used? → A: Include a synthetic-data caveat section explicitly stating that all results were produced on bundled synthetic data and do not constitute validated clinical performance.
- Q: How should a panel behave when its required SPEC-011 input file is missing? → A: Render a visible unavailable panel that names the missing file and states what SPEC-011 command produces it; register the unavailable state in `outputs/figures/manifest.json`.
- Q: Should the dashboard CLI support optional subgroup inputs when they are absent from SPEC-011 output? → A: Yes. Subgroup fairness panel renders an explicit sparse-data or unavailable state when subgroup columns are absent from `predictions_oof.csv` or source data.
- Q: What is the minimum figure size for SPEC-012 panels? → A: 1600 × 900 pixels, consistent with SPEC-007 and SPEC-010 EDA panels.
- Q: Should analytic artifacts share `outputs/figures/manifest.json` with EDA artifacts or use a separate manifest? → A: Shared manifest. Analytic entries carry `"type": "analytic"`; EDA entries carry `"type": "eda"`. One registry for pipeline QA; type field enables filtering.
- Q: What is the calibration-sparsity threshold that triggers Panel 2's warning panel instead of the calibration belt? → A: Warn (render warning panel) when fewer than 3 non-empty calibration bins exist OR any non-empty bin has fewer than 10 samples.
- Q: How many confirmed events are needed for Panel 7 to show aggregate median+band instead of individual trajectories? → A: 5 confirmed events. Below 5, render individual trajectories with a sparse-data warning.
- Q: When `config/costs.yaml` is absent, does the CLI abort the full run or only fail Panel 4? → A: Panel 4 only. Render Panel 4 as an explicit unavailable/error panel naming the missing file; all other panels render normally; CLI exits 0.
- Q: What file path should Panel 10 probe for learning-curve data generated by SPEC-011? → A: `{model_dir}/learning_curve.csv` — flat file alongside other SPEC-011 outputs. Absent → explicit unavailable panel.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Render a Full Analytic Report from Bake-off Outputs (Priority: P1)

A researcher completed a SPEC-011 bake-off run and needs a single command that reads all modeling artifacts and writes a complete analytic dashboard without re-running any model.

**Why this priority**: The analytic dashboard is the primary communication artifact for the model bake-off. Reviewers who cannot retrain models must be able to reproduce figures from saved outputs.

**Independent Test**: Run the dashboard CLI pointing at a directory of SPEC-011 fixture artifacts; assert all 11 required panel PNGs and the model card exist, are at least 1600 × 900 pixels, and appear in `outputs/figures/manifest.json`.

**Acceptance Scenarios**:

1. **Given** all required SPEC-011 output files exist, **when** the dashboard CLI runs, **then** it writes all 11 required panel PNGs and `model_card_tripod_ai.md` under the configured analytic output directory.
2. **Given** an optional SPEC-011 input is absent, **when** the dashboard CLI runs, **then** the affected panel renders an explicit unavailable state naming the missing file and the remaining panels render normally.
3. **Given** the dashboard CLI is run twice with identical inputs, **when** outputs are compared, **then** every panel is pixel-identical (deterministic rendering).
4. **Given** a caller supplies a custom output directory, **when** the CLI runs, **then** all artifacts are rooted in that directory and the model card references the exact paths used.

### User Story 2 - Review Model Leaderboard and Headline Metrics (Priority: P1)

A modeling reviewer needs a single leaderboard figure that compares all bake-off models using imbalance-appropriate headline metrics with confidence intervals and correct metric emphasis.

**Why this priority**: The leaderboard is the first figure a reviewer examines. Incorrect metric ordering (e.g., AUROC or accuracy as primary) would undermine the honest evaluation framing required by P7.

**Independent Test**: Render Panel 1 from `metrics_summary.csv`; assert models are sorted by AUPRC, AUPRC column is visually primary, AUROC is secondary or absent, accuracy does not appear as a headline column, and CI bounds are present for AUPRC, recall at fixed precision, and Brier score.

**Acceptance Scenarios**:

1. **Given** `metrics_summary.csv` is available, **when** Panel 1 renders, **then** models are sorted descending by AUPRC.
2. **Given** AUROC values are present in `metrics_summary.csv`, **when** Panel 1 renders, **then** AUROC appears as a secondary column and is not labeled as primary or headline.
3. **Given** accuracy is derivable from available data, **when** Panel 1 renders, **then** accuracy does not appear as a headline metric.
4. **Given** confidence intervals are present in `metrics_summary.csv`, **when** Panel 1 renders, **then** CI bounds are shown for AUPRC, recall at fixed precision, and Brier score.
5. **Given** a model's rare-event denominator is explicitly noted in summary metadata, **when** Panel 1 renders, **then** the denominator note appears on or adjacent to that model's row.

### User Story 3 - Audit Calibration and Decision Curve (Priority: P1)

A clinical-safety reviewer needs calibration and decision-curve diagnostics to assess whether model scores are clinically interpretable and to understand net benefit across probability thresholds.

**Why this priority**: Raw discrimination metrics (AUPRC, AUROC) do not capture score reliability. A model that discriminates well but is poorly calibrated would produce misleading alert probabilities for clinical interpretation.

**Independent Test**: Render Panel 2 from `calibration_table.csv` and `decision_curve.csv`; assert calibration content is present, Brier score is shown, decision-curve baseline lines are present, and a sparse-data warning panel is rendered when calibration bins are too sparse.

**Acceptance Scenarios**:

1. **Given** `calibration_table.csv` is available, **when** Panel 2 renders, **then** it shows a calibration plot or belt with observed versus predicted probabilities.
2. **Given** Brier scores are present in calibration data, **when** Panel 2 renders, **then** Brier score is shown in the panel summary.
3. **Given** `decision_curve.csv` is available, **when** Panel 2 renders, **then** it shows net benefit across threshold probabilities with treat-all and treat-none baselines.
4. **Given** calibration bins are too sparse for a reliable belt, **when** Panel 2 renders, **then** it displays an explicit sparse-data warning panel rather than a misleading calibration visual.

### User Story 4 - Explore Operating Points and Threshold Tradeoffs (Priority: P1)

A clinical reviewer needs a threshold-explorer panel to compare precision, recall, false-positive rate, alert burden, and number-needed-to-alert across the full operating-point grid.

**Why this priority**: Alert burden and false-positive rates directly affect staff workload and participant safety. Threshold selection without this context would be clinically irresponsible.

**Independent Test**: Render Panel 3 from `operating_points.csv`; assert precision, recall, false-positive rate, alert burden, and number-needed-to-alert are shown; assert the three default highlighted points are marked when available.

**Acceptance Scenarios**:

1. **Given** `operating_points.csv` is available, **when** Panel 3 renders, **then** it shows precision, recall, false-positive rate, alert burden, and number-needed-to-alert across the threshold grid.
2. **Given** a threshold with highest recall at precision >= 0.80 exists in the grid, **when** Panel 3 renders, **then** that operating point is highlighted and labeled.
3. **Given** a threshold with lowest alert burden at recall >= 0.80 exists, **when** Panel 3 renders, **then** that point is highlighted and labeled.
4. **Given** a model default threshold is available, **when** Panel 3 renders, **then** that point is highlighted and labeled.

### User Story 5 - Review Alarm Cost Analysis (Priority: P1)

A program manager needs a cost figure that traces false-positive rate through false alerts to nurse-hotline call volume to personnel cost, using configurable cost assumptions with sensitivity ranges.

**Why this priority**: Without a cost frame, the choice of operating point lacks operational justification. All finance assumptions must come from a config file so the analysis remains auditable and reproducible.

**Independent Test**: Render Panel 4 from `operating_points.csv` and `config/costs.yaml`; assert cost assumptions come from the config file, sensitivity ranges are shown, assumed participant-days and cost-per-call are labeled, and the panel renders an explicit unavailable/error state (not hardcoded costs) when `config/costs.yaml` is absent.

**Acceptance Scenarios**:

1. **Given** `config/costs.yaml` and `operating_points.csv` are available, **when** Panel 4 renders, **then** it shows false-positive rate → false alerts → call volume → cost chains.
2. **Given** sensitivity ranges are defined in `config/costs.yaml`, **when** Panel 4 renders, **then** cost sensitivity bands are shown for each range defined in the config.
3. **Given** `costs.yaml` defines assumed participant-days and cost-per-call, **when** Panel 4 renders, **then** those values are labeled on the figure.
4. **Given** `config/costs.yaml` is absent, **when** the dashboard CLI runs, **then** Panel 4 renders an explicit unavailable/error panel naming the missing file, the remaining panels render normally, and the CLI exits 0.

### User Story 6 - Inspect Feature Importance and Local Explanations (Priority: P2)

A modeling reviewer needs an explainability panel that shows global feature importance and, where available, local explanations for selected high-risk alerts, with clear labeling of the explanation method used.

**Why this priority**: Understanding which features drive alerts is required for any clinical or safety review, but fabricated SHAP values would be worse than showing nothing.

**Independent Test**: Render Panel 5 with and without `feature_importance.csv` and `local_explanations.csv`; assert global importance is shown when available, local explanations are shown when available, method is labeled, and unavailable states render an explicit panel rather than fabricated values.

**Acceptance Scenarios**:

1. **Given** `feature_importance.csv` is available, **when** Panel 5 renders, **then** it shows global feature importance with ranked features and importance values.
2. **Given** `local_explanations.csv` is available, **when** Panel 5 renders, **then** it shows local explanations for selected high-risk predictions with the explanation method labeled.
3. **Given** SHAP values are unavailable but model-native importance is available, **when** Panel 5 renders, **then** it shows model-native importance and labels the method clearly.
4. **Given** neither `feature_importance.csv` nor `local_explanations.csv` is available, **when** Panel 5 renders, **then** it renders an explicit unavailable panel without fabricating values.

### User Story 7 - Visualize CV-vs-Heat Discrimination (Priority: P2)

A domain reviewer needs a panel that shows how risk or alert scores vary by cardiovascular-vs-heat trajectory direction — body-water direction, BP trend, HR trend, skin-temperature trend, and heat index where available — to confirm the model discriminates intended physiological patterns.

**Why this priority**: Project Lullaby's core purpose is distinguishing CV burden from heat strain. A model that cannot discriminate these trajectory directions does not meet clinical fidelity requirements.

**Independent Test**: Render Panel 6 from `predictions_oof.csv` and source data; assert the panel shows risk score by the required vital-direction dimensions and marks confirmed CV and heat outcomes where available.

**Acceptance Scenarios**:

1. **Given** `predictions_oof.csv` and source vitals data are available, **when** Panel 6 renders, **then** it shows risk score by body-water direction, BP trend, HR trend, and skin-temperature trend.
2. **Given** heat-index data are available, **when** Panel 6 renders, **then** heat index is also used as a discrimination dimension.
3. **Given** confirmed CV and heat outcomes are available, **when** Panel 6 renders, **then** those outcomes are marked on the panel.
4. **Given** trajectory direction data are unavailable, **when** Panel 6 renders, **then** it renders an explicit unavailable panel explaining which input is missing.

### User Story 8 - Analyze Lead-Time Before Confirmed Events (Priority: P2)

A reviewer needs a lead-time panel showing how risk scores evolve before confirmed cardiovascular events, with a days-before-event axis, event-day marker, non-event baseline, and uncertainty bands.

**Why this priority**: Lead time is a key measure of the model's early-warning utility. Too few events require individual trajectory display rather than suppressing the view entirely.

**Independent Test**: Render Panel 7 with ≥ 5 confirmed events (median and band) and with < 5 events (individual trajectories); assert the panel adapts to event count and always shows the appropriate sparse-data or unavailable framing.

**Acceptance Scenarios**:

1. **Given** confirmed event records are available, **when** Panel 7 renders, **then** it shows risk-score trajectory on a days-before-event axis with an event-day marker.
2. **Given** 5 or more confirmed events exist, **when** Panel 7 renders, **then** it shows median trajectory with uncertainty band and a non-event comparison baseline.
3. **Given** fewer than 5 confirmed events exist, **when** Panel 7 renders, **then** it shows individual trajectories with a visible sparse-data warning.
4. **Given** no confirmed event records exist, **when** Panel 7 renders, **then** it renders an explicit unavailable panel.

### User Story 9 - Review Grouped CV Fold Structure (Priority: P2)

A methods reviewer needs a fold-structure panel confirming participant-group assignments, per-fold class counts, fold-level AUPRC and recall-at-precision variance, and an explicit no-leakage annotation.

**Why this priority**: The fold-structure panel is the visual audit trail for the leakage-free cross-validation required by SPEC-011. Without it, a reviewer must re-run the bake-off to verify fold integrity.

**Independent Test**: Render Panel 8 from `predictions_by_fold.csv` and `metrics_by_fold.csv`; assert fold assignment, per-fold positives/negatives, and per-fold AUPRC variance are shown and the no-leakage annotation is present.

**Acceptance Scenarios**:

1. **Given** `predictions_by_fold.csv` is available, **when** Panel 8 renders, **then** it shows fold assignment by participant and per-fold positives and negatives.
2. **Given** `metrics_by_fold.csv` is available, **when** Panel 8 renders, **then** it shows per-fold AUPRC and recall-at-precision variance.
3. **When** Panel 8 renders under any condition, **then** it includes a visible no-leakage annotation stating that no participant appears in both training and validation within any fold.

### User Story 10 - Audit Subgroup Fairness (Priority: P2)

A fairness reviewer needs a subgroup audit panel showing AUPRC or recall-at-precision for race/ethnicity, insurance, AC access, and health literacy subgroups, with denominators and explicit sparse-subgroup warnings.

**Why this priority**: P10 (equity-centered design) requires the product to surface disparities across the enrolled population's lived constraints. Subgroup metrics without denominators cannot be responsibly interpreted.

**Independent Test**: Render Panel 9 with and without subgroup columns; assert denominators are shown, sparse-subgroup warnings appear where counts are too small, and overinterpretation warnings appear where positives-per-subgroup are very small.

**Acceptance Scenarios**:

1. **Given** subgroup columns are available in `predictions_oof.csv` or source data, **when** Panel 9 renders, **then** it shows AUPRC or recall-at-precision by available subgroups with N and positive-event count.
2. **Given** a subgroup has `n_in_subgroup < 10`, **when** Panel 9 renders, **then** it suppresses the metric, shows the denominator, and displays a sparse-subgroup warning.
3. **Given** a subgroup has `n_events_in_subgroup < 3`, **when** Panel 9 renders, **then** it displays the metric with a visible overinterpretation caution annotation beside it.
4. **Given** subgroup columns are absent from all inputs, **when** Panel 9 renders, **then** it renders an explicit unavailable panel explaining which input is needed.

### Edge Cases

- If `metrics_summary.csv` is absent, Panel 1 MUST NOT infer metrics from raw predictions; it MUST render an explicit unavailable panel naming the missing file and the SPEC-011 command that generates it.
- If `config/costs.yaml` is absent, Panel 4 MUST render an explicit unavailable/error panel naming the missing file; it MUST NOT use hardcoded cost assumptions; the CLI MUST NOT abort.
- If calibration bins are too sparse (fewer than 3 non-empty bins or any non-empty bin with fewer than 10 samples), Panel 2 MUST render a visible sparse-data warning rather than a misleading figure.
- If fewer than three operating-point candidates are available for the default-point highlighting in Panel 3, only available candidates are highlighted; the panel does not fabricate operating points.
- If `local_explanations.csv` is present but contains no rows for the selected high-risk threshold, Panel 5 renders a note stating no high-risk examples met the selection criteria rather than rendering a blank panel.
- If trajectory direction fields are absent from source vitals data, Panel 6 renders an unavailable panel explaining the missing columns.
- If event records exist but all are after the observation window end for Panel 7, the lead-time panel renders an explicit note that no pre-event window observations are available.
- If fold or repeat columns are missing from `predictions_by_fold.csv`, Panel 8 renders an unavailable panel rather than constructing synthetic fold assignments.
- If subgroup columns exist but contain only one unique value across all participants, Panel 9 does not show subgroup comparison for that column and records a note that no variation was observed.
- If a required panel's output PNG already exists at the output path, the CLI overwrites it deterministically rather than skipping rendering.
- If a cost-config sensitivity list in `config/costs.yaml` contains only one value, Panel 4 shows a point estimate instead of a sensitivity band without crashing.
- If `bakeoff_summary.json` is absent, the model card is still generated from available artifact files and notes that the bake-off summary was not found.

### Cost Configuration Contract

`config/costs.yaml` MUST define:

```yaml
currency: USD
nurse_hotline:
  cost_per_call: 42.00
  minutes_per_call: 18
  nurse_hourly_cost: 85.00
alert_workflow:
  survey_review_minutes: 4
  false_positive_call_probability: 0.65
  true_positive_call_probability: 0.90
volume_assumptions:
  participants: 200
  participant_days: 8400
  alerts_to_calls_multiplier: 1.0
sensitivity:
  cost_per_call: [25, 42, 75]
  false_positive_call_probability: [0.40, 0.65, 0.85]
```

Panel 4 reads this file at runtime. Changes to cost assumptions require only updating `config/costs.yaml`, never editing plotting code.
