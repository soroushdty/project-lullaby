# Feature Specification: Static Interactive Dashboard Viewer

**Feature Branch**: `014-interactive-dashboard-viewer`

## Objective
Provide an interactive, browser-based UI to explore the analytic and descriptive dashboards generated by Project Lullaby. To maintain absolute clinical traceability (P2), the UI must act strictly as a viewer for the pre-generated PNG artifacts and `manifest.json`, rather than a live application that re-renders or manipulates data on the fly.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Navigate Pipeline Artifacts (Priority: P1)
As a clinical reviewer, I want to open a single web page and browse through all generated dashboards (Cohort Overview, Heat Environment, Model Leaderboard) without navigating a raw filesystem.

**Why this priority**: Essential for non-technical stakeholders to consume the project's outputs securely and easily.

**Acceptance Scenarios**:
1. **Given** a generated `outputs/figures/manifest.json`, **When** the web app loads, **Then** a navigation menu is populated with categories (e.g., "Analytic", "EDA Core", "EDA Longitudinal") based on the manifest entries.

### User Story 2 - View Artifact Metadata (Priority: P1)
As a data scientist, I want to see the warnings, missingness caveats, and input data paths alongside the rendered dashboard so I understand its limitations.

**Why this priority**: Prevents misinterpretation of synthetic or incomplete data (P7 Honest Evaluation).

**Acceptance Scenarios**:
1. **Given** an artifact with `warnings` in the manifest, **When** I view that artifact in the UI, **Then** a prominent warning banner displays the specific caveat strings.

### User Story 3 - Static Hosting Compatibility (Priority: P2)
As a devops engineer, I want to deploy the dashboard to any standard static file host (e.g., GitHub Pages, AWS S3) without requiring a Python backend.

**Why this priority**: Simplifies deployment and guarantees the UI cannot alter data (P6 Distribution Integrity).

**Acceptance Scenarios**:
1. **Given** a built React app, **When** served via a simple HTTP server (e.g., `python -m http.server`), **Then** all routing and image loading functions correctly.

## Requirements *(mandatory)*

### Functional Requirements
- **FR-001**: The application MUST load `manifest.json` dynamically at runtime via a relative fetch (e.g., `fetch('./manifest.json')`).
- **FR-002**: The application MUST group artifacts in the sidebar by their semantic prefix (e.g., `analytic_`, `eda_core_`, `eda_longitudinal_`).
- **FR-003**: The UI MUST render the exact `path` string from the manifest as an `<img>` tag.
- **FR-004**: The UI MUST display the artifact `title`, `spec`, and `metadata` below or beside the image.
- **FR-005**: If an artifact is marked `"available": false` in metadata, the UI MUST display the unavailability reason instead of attempting to load an image.

### Constitution Alignment (P1-P10)
- **P1 SDD**: Designed via SPEC-014 before implementation.
- **P2 Reproducibility**: The UI does not compute data; it only displays verified pipeline outputs.
- **P6 Distribution**: The app compiles to pure static HTML/JS/CSS, easily distributable alongside the pipeline outputs.
- **P10 Equity**: The UI provides a high-contrast, accessible way for non-technical domain experts to review the system's claims.

## Success Criteria *(mandatory)*
- **SC-001**: A reviewer can launch the app locally using a single command (e.g., `npm run start` or `python -m http.server`) from the `outputs/figures/` directory.
- **SC-002**: All 16+ artifacts currently registered in the manifest are navigable and legible in the UI.

## Assumptions & Dependencies
- **Depends on**: The `outputs/figures/manifest.json` schema stabilized in SPEC-004 through SPEC-012.
- **Tech Stack**: A lightweight toolchain like Vite + React, or plain HTML/vanilla JS to minimize the `node_modules` burden on the repository.
